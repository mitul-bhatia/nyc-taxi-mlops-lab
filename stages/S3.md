# S3: serving, promotion and blue-green (Day 1, 16:30–18:15)

**Goal:** the app quotes trips with the `champion` model instead of the static median. Promoting a new champion is a reviewed click, and so is rolling it back. A new version of the app reaches riders through a blue-green switch, with the old version still running in case you need it.

## Recall check (5 minutes, no agent)

1. Blue-green or rolling update: what does each cost you, and what does each protect you from?
2. What is the difference between a health check and a smoke test?
3. In GitHub Actions, what does an environment with required reviewers change about a job?
4. Why put the champion behind an alias rather than pin serving to a version number?

## Given

- `contracts/serving-openapi.yaml` (frozen): serving's `/predict` (features.yaml's inputs), `/model`, `/reload`.
- `serving/`: one container per alias (`serving-champion`, `serving-challenger`), loading `models:/trip-duration@<alias>` at start-up; `POST /reload` swaps to what the alias points at now, and the old model answers until the new one has loaded.
- The app now asks serving (through Traefik, port 8001) and falls back to the static median if serving is slow, down, or has no champion yet. Its response's `model` says which one answered.
- `deploy/compose.web.yaml` (Traefik, `app-blue`, `app-green`), `deploy/compose.serving.yaml`, Traefik's routes in `deploy/traefik/web/`, and `deploy/web.sh`: `prepare`, `live`, `tag`, `smoke`, `switch`, `reload`, `status`. Which colour is live is kept in a Docker volume, not in your checkout.
- `.github/workflows/serving.yaml`: builds and deploys serving, like `platform.yaml`.

## Build

1. **Serving:** add a `platform_private_ip` output to `infra/live/outputs.tf` and apply. Then `gh variable set MLFLOW_TRACKING_URI --body "http://$(terraform -chdir=infra/live output -raw platform_private_ip):5000"` and `gh variable set LAB_SERVING --body on`, and run the serving workflow (`gh workflow run serving.yaml`). Its last step shows what each container loaded: the challenger, and a 503 for the champion until you promote one. The app can't reach serving yet (that's step 2's Traefik), so it keeps quoting the static median.
2. **Blue-green:** change your CD to deploy with `deploy/compose.web.yaml`: deploy to the idle colour, check it, switch, keep the old one. Add a way to roll back without deploying. The first deploy with the new stack has a gap of about 15 seconds while Traefik changes config; after that, none.
3. **Promotion:** create the `production` environment with yourself as required reviewer:
   `gh api -X PUT "repos/$(gh repo view --json nameWithOwner -q .nameWithOwner)/environments/production" --input - <<< "{\"reviewers\": [{\"type\": \"User\", \"id\": $(gh api user -q .id)}], \"prevent_self_review\": false}"`.
   Write `.github/workflows/promote.yaml`: on `workflow_dispatch`, in that environment, on your app host's runner. Promote the challenger (or a version you name) to `champion` only if the pipeline evaluated it, record the outgoing champion, make serving use the new one, and check `/predict`. Run it and approve it.
4. **Rollback:** roll back the app (switch colours) and time it. Then say how you'd roll back the model: you have one gated version today, so there's no previous champion yet. You'll do it for real in S8, when a retrain brings a second one.

## Decision points (one record each in `decisions/`)

- **Load at start-up or reload on alias change:** how does serving pick up a new champion, and what does a rider see meanwhile?
- **What triggers the blue-green switch:** which checks must pass, and who or what flips it.

## Done when

- `make check` passes; the CD, serving and promote workflows are green.
- `curl -X POST http://<app_public_ip>/predict ...` answers with `"alias": "champion"` and the version you promoted.
- `deploy/web.sh status` on the host shows both colours, the live one on your latest commit.
- `production` has you as required reviewer, and a promotion run waited for your approval.
- Your two new decision records exist.
