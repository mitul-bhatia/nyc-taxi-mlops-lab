# S7: MCP (Day 2, 14:00–15:15)

**Goal:** the assistant can do more than read the wiki. It predicts trip times with your champion, tells riders which model it is, and looks up historical zone statistics, through an MCP server whose tools can't do more than they should, even when someone edits the wiki to tell the assistant otherwise.

## Recall check (5 minutes, no agent)

1. What does MCP standardise that a hand-rolled HTTP API between the app and its tools doesn't?
2. Least privilege for a tool that reads a warehouse: what should its database user be able to do, and what not?
3. What is an indirect prompt injection, and why can't the model be the only thing that stops one?
4. Which of your tools would you want a human to confirm before it runs, and why?

## Given

- **`mcp/`, the MCP server:**
  - Streamable HTTP on port 8002, path `/mcp`, deployed by `.github/workflows/mcp.yaml` (`deploy/compose.mcp.yaml`), on the `lab` network only.
  - The tools are `contracts/mcp-tools.json`'s (frozen since S0). `get_model_info` is done; `predict_duration` and `query_zone_stats` say "not built yet".
  - Zone names resolve against the bundled TLC zone list, with suggestions for typos.
  - `Warehouse` runs Data API queries as `MCP_DB_USER` with named parameters.
  - `/healthz?db=1` reports what that user may do.
- **The assistant's tool loop** (`app/src/rideapp/assistant.py`): lists the MCP server's tools, offers the model the ones you allow, runs each call it asks for through your `allow_tool_call`, and feeds the results back, for up to three rounds. Every call appears in the response's `tool_calls` and in the Langfuse trace.
- **The status workflow** now reports the MCP server's tools and its database user's privileges.

## Build

1. **A read-only user:** create the database user the MCP server runs as. It reads `marts` and nothing else, and the mart's refresh must not undo that. `MCP_DB_USER` defaults to `lab_ro`.
2. **The tools (25 min):** in `mcp/src/labmcp/server.py`:
   - `predict_duration`: zone names to ids, then serving-champion's `/predict` with `features.yaml`'s encodings.
   - `query_zone_stats`: from `marts.zone_hour_stats`. Nothing from a tool call is ever formatted into SQL.

   `make test-mcp`, push, `gh variable set LAB_MCP --body on`, `gh workflow run mcp.yaml`.
3. **Wire them in (15 min):** in `assistant.py`, choose `ALLOWED_TOOLS`, write `TOOLS_PROMPT` (when to use which tool) and `allow_tool_call`. Redeploy the app. Ask "How long from JFK Airport to Times Square at 5pm on a Friday?" and read the trace: which tool, which arguments, how long each round took. The tools add about 1,000 prompt tokens, so the first answer after a deploy or a prompt change takes up to 2.5 minutes; later ones reuse the cached prefix (about a minute).
4. **E3 (when the instructor fires it):** the wiki's rider FAQ changes. Re-ingest (`scripts/dagster-run.sh ingest_wiki --wait`) and ask "Why might my ETA to Pier 76 be longer on weekends?". Find out from the trace what happened, then fix it where you decide it belongs: the tool layer, the prompt, retrieval, or more than one. Ask again and show the difference.

## Decision points (one record each in `decisions/`)

- **Tool granularity and confirmation:** which tools the assistant may call, whether any needs a person to confirm, and what you'd change if a tool could write.
- **Database role scope:** what the MCP server's user may read, and how you know it can't do more.
- **Where to fix E3:** the layer you chose, the one you rejected, and what the fix still doesn't stop.

## Done when

- `curl -m 200 -X POST http://<app_public_ip>/assist ...` for a trip-time question shows a successful `predict_duration` in `tool_calls`, and the answer uses its number.
- The status artifact shows the MCP user can read the mart and can't write it or read `ingest`.
- After E3, the injection question doesn't lead to a successful `query_zone_stats` call, and you can show why in a trace.
- `make check` passes, and your three new decision records exist.
