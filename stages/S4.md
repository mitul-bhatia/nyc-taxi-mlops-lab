# S4: restore service (Day 2, 10:00–10:45)

**Goal:** yesterday's system answers riders again with the champion, and you know exactly what broke overnight, how long each fix took, and which of those fixes a machine should do next time. Nothing new gets built today until this is done.

## Recall check (5 minutes, no agent)

1. What's the difference between an RTO and an RPO? Which one matters for this lab overnight?
2. What is toil? Give one example from yesterday.
3. Your app answers HTTP 200 with a wrong number. Which kind of check catches that, and which can't?
4. A Docker container has `restart: unless-stopped`. What happens to it when the host reboots, and when its process exits?

## What happened overnight (E2)

The session ended at the 4-hour mark: Learner Lab stopped your EC2 hosts, and your terminal's credentials expired about two hours later. You stopped RDS and the notebook and paused Redshift at 18:45, so they're still down. Start Lab has just started the hosts again. Your laptop may be on a different network than yesterday.

## Given

- `scripts/health.sh`: read-only, one line per piece (session, laptop IP, hosts and runners, RDS, Redshift, notebook, what `/predict` answers with, the last status run). Exit 0 only when everything is OK.
- `runbooks/000-template.md`: the runbook format. One row per broken thing, written while you fix it.
- The status artifact now also says what state RDS and Redshift are in, as the platform host sees them.

## Build

1. **Triage (10 min):** Start Lab, export the new credentials, run `scripts/health.sh`. Before fixing anything, copy the template to `runbooks/restore.md` and write down every FAIL and WARN as a row.
2. **Restore by hand (15 min):** bring each piece back and time it. Watch what comes back by itself once RDS is up: Dagster, MLflow and serving all have their own way back. Which ones, and how long after? `gh workflow run status.yaml` when you think you're done.
3. **Automate (15 min):** pick what a machine should do tomorrow, and do it: a restore script, something that runs when a host boots, or both. Leave the rest in the runbook as steps, with the reason.
4. **Prove it (if time allows):** pause Redshift, reboot the platform host (`aws ec2 reboot-instances`) and touch nothing. Does it come back on its own? How long did it take?

## Decision points (one record each in `decisions/`)

- **What to automate and what to leave as a documented step:** which steps, what triggers the automation, and what it must never do on its own.

## Done when

- `scripts/health.sh` exits 0.
- `curl -X POST http://<app_public_ip>/predict ...` answers with `"alias": "champion"`.
- The status workflow is green after your restore, and it reports RDS and Redshift `available`.
- `runbooks/restore.md` has a row for everything you found, each with the time it took.
- Your automation is committed, and your decision record says why it's that and not more.
